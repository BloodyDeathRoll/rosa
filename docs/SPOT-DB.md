### Water sources are re-matched after every seed (2026-09-26)

A new spot gets its pollution source by re-running both matches and committing `data/water/bathing.yaml`:
`rosa-pipeline bathing --match nsw` (live GeoJSON), plus `bathing --match eea --xlsx <workbook>` for an EU
region (steps in `docs/WATER-SOURCES.md`). A spot with no official site within 2 km reads "no data".
Clarity needs nothing: it samples every spot automatically.

### Shore normals are checked after every seed (2026-09-03)

`offshore_direction` comes from the nearest OSM coastline segment, and at a headland, a bay mouth
or a sand spit that normal can point along the shore or into land. `bathy` then cuts its profile
over dry ground and writes it without failing, so the committed profile carries land elevations in
a field named `depth_m`. Three spots in the East Africa pass did exactly this.

`tools/spot-seed/aim_normal.py` sweeps the seaward bearing every 2 deg on the local GEBCO grid and
scores each 0.25-18 km ray. **It reports only - it never edits a YAML**, for the same reason
`horizon`, `atl24` and `sdb` do not: re-aiming a normal moves published heights.

Read the result with these rules:

- **`offshore_depth_m <= 0` is the real defect.** The ray never reached water.
- **Land past 0.25 km is a defect; land at 0.25 km is not.** GEBCO's ~450 m cell straddles the
  beach, so the first sample reports the land side at a correctly placed spot. 104 of 1299
  committed profiles carry 3+ land samples and every one still reaches real water.
- **Never take the sweep's global argmax.** Along-shore rays are land-free and usually score well,
  so the argmax aims spots down the coast. Read the bearing table and pick the middle of the open
  arc.
- **Check the pin before re-aiming.** A ray that crosses land often means the coordinate is on the
  wrong side of a spit, and re-aiming would fit a good profile to the wrong water.

- **Three angles describe the same coastline and are guard-tested against each other**: `shore_normal` aims the depth ray the physics marches AND, since 2026-09-11, draws the shoreline plane the GRIB wave samplers keep to (a wet grid node more than ~5.5 km behind the pin's plane is on the other side of land - `geo.nearest_wet`, `docs/CALIBRATION.md` 2026-09-11), `offshore_bearing` aims the sample point, `offshore_direction` is where OFFSHORE WIND blows from. (A spot whose ray disagreed by 102° marched swell up a hillside and read 0.0-0.1 m all day.)
- **`shore: sand | rock | reef | mixed` is optional and unset everywhere (2026-09-28).** It exists for the web's swim mode only (rock / reef = "not a swimming beach" banner instead of a rating); nothing derives it, nothing scores on it, and `publish.py` omits the key when unset so today's payloads are unchanged. Set it by hand from local knowledge, like `tide_best`.
- **A spot's `lat`/`lon` is the ONLY place its location is written down.** `offshore_point` is derived, never stored (aim it with pin-relative `offshore_km` + `offshore_bearing`); the absolute field now raises.
- **Bathymetry follows the pin.** Move a spot → its profile is stale → delete it and re-cut (`rosa-pipeline bathy --spot <id>`). Remove a spot → its profile is deleted. Never leave an unused profile behind. Profiles record the `origin` pin they were cast from so staleness is detectable.
- **Staleness is now detected at PUBLISH time too, not only by pytest** (2026-08-16). `DepthProfile.matches_spot` existed but nothing on the publish path called it, so a pin or `shore_normal` edit pushed without a local test run shipped silently - there is no CI, and the VM cron is `git pull` -> `run --all`. `run` now prints `warn: <spot>: committed bathy profile is stale` per affected spot plus a run-summary count. It **warns and keeps publishing**: skipping or substituting depths would move heights fleet-wide, which is a tuning change. Fires on nothing today (265/265 profiles match).
- **Profiles never re-cut themselves.** `run --all` READS profiles and the cron never calls `bathy`, so a schema addition reaches the committed DB only when someone runs `bathy --all` and commits. That gap is real and has bitten twice: on 2026-08-15 **153 of 199 profiles were still missing `missing_samples`**, a key added 2026-08-07. `from_dict` ignores unknown keys, so nothing breaks - it just silently stays behind. Re-cut the fleet in the same change that adds a key. A full sweep is ~199 rate-limited OpenTopoData requests (~4 min); diff the result against the committed set before installing it, and expect **added keys only** - a changed depth means GEBCO moved under you and is a separate decision.
- **Four QC counters, all report-only, all persisted so the DB can be grepped:** `land_samples` (ray points on land -> bad shore-normal), `missing_samples` (source gap; NOT folded into land, since `nan <= 0` is False and a hole was invisible to every QC path), and since 2026-08-15 `non_monotone_samples` (wet samples deeper than the one before, walking the physics march's own order) and `deepest_is_reference` (is `depths[0]` actually the deepest wet point?). The last two make visible the geometry the shoaling march's whole premise depends on: **87/199 rays are non-monotone and 17/199 have their deepest sample inside the 18 km reference** - not a rare shape, and previously invisible. `bathy` prints all four on one warning line. See `docs/ALGORITHM.md` for what the march does about it.
- **Since 2026-09-11 the pipeline and the seeding tool read the SAME grid**: every committed profile is cut from the local `GEBCO_2024.nc` (`bathy --source local`, the default; OPEN-ITEMS 17 applied). What follows is the history of why. **The pipeline's seabed source and the seeding tool's were NOT the same grid, and they disagreed near shore.** `bathy` reads `gebco2020` through OpenTopoData; `tools/spot-seed` reads the local `GEBCO_2024.nc`. On the steep and deltaic Mexican Pacific the two part company badly - at la-ticla the API reads +129 m of hillside 1 km out along a bearing where the local grid reads 8 m of water, and at san-agustinillo the API puts 280 m of water 250 m off the beach where the local grid reads 1 m. The committed fleet is all API-cut, so the seed stayed on the API for consistency; **a source A/B is an open item (OPEN-ITEMS 17), not something to switch mid-region.** Where they disagree the API is the pessimistic one: the march simply starts deeper, so the spot under-shoals rather than breaking.
- **A third grid now exists, and a way to referee all three.** `rosa-pipeline sdb` samples **CMEMS Global Coastal SDB** (100 m Sentinel-2 satellite-derived bathymetry, DOI 10.48670/mds-00364) along each committed ray and reports where it disagrees; `rosa-pipeline atl24` grades any of them against **ICESat-2 ATL24** lidar, which is measured seafloor rather than a third opinion. Both are hand-run: **`sdb` writes nothing without `--apply`, and `atl24` cannot write at all** - same discipline as `horizon` and the cam tools. SDB is a 0-35 m product with a ~116 m cell, so it reaches the first one or two ray points and nothing deeper: measured over the Maldives it returns a gated reading at 23/23 spots at 0.25 km, 18/23 at 0.5 km and 1/23 at 1 km. Patching those points is a **source swap, not the invented shallow samples `docs/ALGORITHM.md` forbids** - where SDB has no reading the GEBCO sample stands, there is no interpolation along the ray, and the merge is not one-way (a deeper SDB reading wins too, or it would be a thumb on the scale). A patched profile says so: its `source` names both grids and `sdb_patched_km` lists the points. **It is not the default and must not become one without the A/B in OPEN-ITEMS 23**, because it moves published heights. Attribution is required in the footer for anything built on it: "Generated using E.U. Copernicus Marine Service Information; https://doi.org/10.48670/mds-00364"; free of charge is guaranteed only to **2028-06-30**. ATL24 is NASA CC0 and reaches ~40 m; it is reachable without an Earthdata login through SlideRule, which refuses a box needing more than 300 granules (the whole Maldives needs 341), so `atl24` splits the box and recurses. **ICESat-2 flies a 91-day repeat orbit, so it can never fill a ray** - over the Male atolls the nearest photon sits 0.9-4.0 km from most named breaks. It is a referee, not a source.
- **`data/spots/derived/bathy/bathy_elevations.json` is a capture, not a profile** - the raw elevations map that `bathy --fixtures <dir>` replays for offline re-cuts. Iterate spot ids from `load_spots()`, never `BATHY_DIR.glob("*.json")`, or `DepthProfile.from_dict` raises `KeyError: 'samples'` on it. It goes stale exactly when pins move, and a stale capture fails loudly (`no captured elevation for <lat,lon>`) rather than quietly - refresh it with `bathy --all --capture <dir>` in the same sweep.
- **`swell_window` can be DERIVED**: `rosa-pipeline horizon --spot <id>` fans rays over 360° off GEBCO and returns the contiguous open-ocean arc containing the shore normal, clipped to ±90°. **It reports and never applies** (same rule as the cam tool). Thresholds, in order: `HORIZON_MIN_BLOCKER_KM` 1.0 (ignore land the source can't resolve), `HORIZON_LAND_M` 3.0, `HORIZON_DEEP_M` -20. **The ordering test - open water BEFORE land - is load-bearing and must not be dropped.**
- **Adoption rule:** adopt a derived window where the YAML window excludes its own shore normal (an objective fault) or where the height moves <10%; HOLD otherwise. 183/199 adopted 2026-08-02.
- **A derived window is an UPPER BOUND on exposure** - the scan measures ocean visibility at ~450 m, so it cannot see a headland sheltering the break at 50-200 m, nor swell wrapping around a point.
- **Sat-verification loop:** `tools/spot-verify/queue.py` (next batch, weakest-authority-first) → `tools/spot-seed/render.py` (crosshair tiles) → a vision pass per `tools/spot-verify/JUDGING.md` → approved moves edited by hand, then `queue.py --mark`. **A moved pin invalidates its bathy profile and may invalidate its three angles - re-cut and re-derive.** **265/265 pins settled as of 2026-08-16** (257/257 on 2026-08-15, 199/199 earlier that day, was 80/199 on 2026-08-04); `queue.py --status` reads 0 outstanding and the loop stays live for new spots. The Mexico + El Salvador seed ran the loop at add time: every one of its 58 pins was rendered and read before it entered the DB, and four candidates were dropped for failing it (see the playbook's §5 log). **The `approx` tag means the pin is usually in open water** - 11 of the first 12 judged were, by 0.3-19 km, and across the full sweep `approx` was wrong almost every time while OSM surf markers were right almost every time. **A pin ON the waterline can still be wrong for the physics**: GEBCO's ~450 m cell reads a headland as dry, so a pin on a point can leave no clean seaward bearing at all (ollies-point - reverted on 2026-08-04, then closed 2026-08-15 with operator-supplied coordinates and re-aimed 210°/8 km). Judge on the profile's **shallowest wet depth**, not its `land_samples` - the march drops land points already.
- **Every spot carries a `town`, and it is a SEARCH key, not part of the name.** A break is famous under its town's name at least as often as its own - "Puerto Escondido" is three breaks (`zicatela`, `la-punta`, `carrizalillo`), "Tel Aviv" is several - and until 2026-08-16 a search for either found nothing. `town` is derived offline from the nearest OSM `place=city|town|village|hamlet` node within 12 km (nearest wins, but a town or city inside 1.6x the nearest hamlet's distance outranks it), and it ships in both the spot payload and the index. The web matches name + region + town + id, and renders the town as the result row's subtitle only when the name carries no parenthetical of its own. `test_every_spot_carries_a_town` enforces completeness - a new spot without one is invisible to the search its own town would have found. Do NOT fold it into `name`; that reads as "Sayulita (Sayulita)" in every list. The one place a town legitimately becomes the name is where the town IS the spot's common name (`zicatela` is displayed "Puerto Escondido").
- **Coordinate authority ladder:** user-verified > sat-verified (`tools/spot-verify/`, `docs/spot-mapping-approach.md`) > OSM features (ODbL) > google-geocoded > approximation. Each spot is tagged with its source. **Local knowledge always wins; treat every user pin correction as authoritative.** OSM beach polygons ≠ surf spots.
- **Geocoding:** Google **legacy** Places textsearch, plus the **Geocoding API - enabled 2026-08-04** (project + key API-restriction both had to allow it; a `REQUEST_DENIED` naming *"not activated"* is the project, one naming *"key is not authorized"* is the key restriction). Elevation/Static Maps are still NOT enabled. Nominatim/Photon benchmarked far worse on surf POIs (>100 km misses) - don't switch without re-benchmarking. **Neither provider is trustworthy alone on surf-vocabulary names**: on 2026-08-04 Google put "Ollie's Point" 354 km away on a same-named inland Potrero Grande, while Nominatim placed Marbella within 140 m of the satellite pin. Always cross-check against a tile. Google returns the named POI, not the peak: seed or flag with it, never overwrite a verified pin.
- **Cams:** `verify --resolve --apply` swaps a dead id for a replacement **only when the TITLE still matches** - same title = same camera.
